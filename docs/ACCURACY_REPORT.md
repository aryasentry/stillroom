# Accuracy, performance and verification report

Evidence date: **2026-10-11**. This report separates implemented capability from measured evidence. Private real-room recordings were subsequently used for quality diagnosis. Their videos, frames, reconstructed scenes and screenshots remain outside the public evidence directory; no independent physical measurements are available.

## Test material and environment

All bundled room geometry, textures and memory fixtures were procedurally authored for Stillroom and dedicated under CC0-1.0. The room measures 6×5×3 metres in its generator, has 96 modelled objects and 3,888 rendered triangles, and deliberately leaves front/top boundaries open. PLY and SPZ fixtures contain **25,036** sampled Gaussian centres each. They are synthetic rendering/coordinate fixtures, not photogrammetric or Gaussian reconstructions of a physical place.

Fixture provenance and known coordinates are in `fixtures/README.md`, `fixtures/measurements.json` and `scripts/generate_demo.py`. Test host: macOS, Apple M3 with 16 GiB memory, Python 3.13.13 and Node 24.19.0. Recorded browser evidence identifies Headless Chrome 151 with ANGLE Metal on Apple M3. Three.js 0.186.1 and Spark 2.3.1 are pinned in the frontend lockfile. Windows, Linux, Safari, Firefox, mobile hardware and other GPUs have not been runtime-verified.

## Photo-to-room evidence and completion boundary

Implemented: a photos-first library action, existing-photo review, guided capture, immutable original storage, local tool preparation, persistent background attempts, actual stage/counter progress, cancellation/retry, isolated generated-scene preview and explicit acceptance. GLB/PLY/SPZ import and existing memory tools remain available. This workflow does not infer a floor plan or generate missing geometry.

The installer was executed successfully on the Apple M3 host: PyCOLMAP **4.2.1**, NumPy **2.2.6** and Brush CLI **0.3.0** are installed locally, and `pip check` reported no broken requirements. Camera reconstruction uses CPU features/matching; Brush trains the visual Gaussian scene on the local GPU. Native Windows/Linux execution and other GPUs are unverified. The implementation provides pinned checksums/archive paths; those are not runtime evidence.

A native blank-photo subprocess test ran real PyCOLMAP extraction, matching and mapping, returned `needs_photos` with all three input photos unused, and did not train a scene. Manager tests use a controlled subprocess that emits a tiny valid Gaussian PLY to test supervision and format validation; those tests do not demonstrate photogrammetric reconstruction quality.

The positive native trial used **54 synthetically rendered photographs** generated locally for this test. Only image files entered reconstruction: generating camera poses and source geometry were withheld. All 54 photos registered into one connected model with 19,634 sparse points. The 3,000-step run completed in **588.69 seconds**, produced a validated **31,184-splat / 7,360,974-byte Gaussian PLY**, and rendered a recognizable room in the browser from a recovered camera. Soft edges, scattered points and incomplete unseen surfaces remain visible. Other browser verification overlapped this timing, so it is one device observation, not an ETA. [Native evidence](evidence/photo-native-verification.json) records the output hash, engines and profile.

The worker and native children completed under macOS `sandbox-exec` with all network operations denied. Setup downloads had already finished. This is direct OS-level offline evidence for reconstruction, in addition to the separate browser request restriction.

The sparse model's mean reprojection error was **0.300 pixels**. After fitting a similarity transform against all 54 generating camera positions, camera-centre RMSE was **0.000428 m** on this deliberately favourable synthetic scene. That fit supplies otherwise unknown scale and alignment, so it is not an independent distance check or a real-world accuracy claim. [Camera analysis](evidence/photo-camera-accuracy.json) records the method and limits. The generating poses were used only for post-run analysis.

The initial view now comes from a recovered camera near the median camera position. A display rotation estimates upright direction from camera orientations without changing PLY coordinates; the same source-space view and display rotation survive preview, acceptance and archives. This prevents scattered outliers from making the initial bounds-fitted view unusably distant. Physical scale, gravity and floor height remain unmeasured.

Preview quality uses 3,000 training steps, maximum image resolution 960 and 300,000 splats; standard uses 7,000 steps, 1,280 and 750,000 splats. Standard is now the default and additionally enables guided feature matching; Preview keeps the faster matching path. Equal-size frames from one verified video share one camera calibration, while mixed sources retain independent calibration. The recommended extraction target is now 120 frames. Preparation makes bounded 1,600-pixel working JPEGs while preserving source bytes. These are configured limits, not measured device capacity or guaranteed final splat counts. A missing/invalid final PLY fails even when Brush exits zero. Attempts are bounded to two hours and one active reconstruction across the library.

Backend tests cover retained capture budgets, identical-photo deduplication, schema migration, ownership and hash checks, interruption, cancellation of a real descendant process on macOS, missing/corrupt/outside-directory output rejection, stale acceptance, preserved old scans/anchors and portable provenance validation. Additional regressions cover 200-photo completion messages, exact protocol byte limits, exclusive data-root ownership across processes, OS lock release after a crash, Windows process-handle watchdog logic (mocked), and recovered-camera conventions. Frontend tests cover collection membership, limits/HEIC guidance, managed ready-output validation and isolated preview. Browser checks have passed photo selection/removal/deduplication, narrow layout, native insufficient-overlap guidance, cancellation/retry and editor-only undo isolation. The browser-driven native run registered all 54 photos and produced **30,557 splats / 7,213,002 bytes**. Its stored attempt took **586.83 seconds** from creation through acceptance, including preview interaction. The actual scene loaded in preview and was explicitly accepted; a memory was placed, saved and reopened in the rendered room. The generated 19,957,349-byte archive then imported into a separate store with all 109 asset checksums, 54 originals, source camera, display transform and memory anchor preserved. ## Local video extraction

PyAV **18.1.0** decodes MP4/MOV/WebM locally into timestamped JPEG captures. Native decoding tests cover H.264 MP4, MOV container acceptance, a portrait display matrix, VP8 WebM and a WebM with no declared duration. Validation covers malformed and overlong clips, stationary repeated views, cancellation, capture-budget rollback, retained-source ownership, portable provenance and abandoned staging cleanup after restart. Video acceptance and successful decode do not certify a room’s overlap or geometry.

The separate [OS-network-denied extraction](evidence/video-offline-verification.json) decoded 324 frames from a 27-second, 960×720 H.264 synthetic clip, chose 54 distinct views from an 80-frame target, and completed in **1.127 seconds** on this host. It skipped 26 almost-identical candidates. The source is a video encoded from rendered camera views held for six frames each; it does not reproduce handheld motion blur, rolling shutter, automatic exposure changes or real-room capture conditions.

Browser checks exercise real video upload/extraction, timestamped frame review, reload/reopen, narrow layout, an actual decoder failure, retained-video retry, explicit upload abort, and pending-photo preservation. Controlled job responses are used only for deterministic cancellation timing; the real extraction and native result are separate checks.

The [native video browser run](evidence/video-browser-verification.json) selected and registered **54/54** video-derived frames and produced **31,087 splats / 7,338,082 bytes**. The complete browser interaction from video upload through accepted room and ZIP export took **202.875 seconds**; this is a single favorable synthetic sample, not an ETA for another room. The [actual preview](evidence/video-reconstruction-preview.png) was inspected and shows recognizable furniture and room structure, with soft edges and artifacts. The [portable video archive check](evidence/video-archive-verification.json) separately imported all 110 assets, preserving the video, 54 frame timestamps/source hashes, validated scene and recovered viewpoint. No external browser application requests or page errors were observed. Unlike the separate extraction-only sandbox test, this full pipeline run was not OS-firewalled.

## Private room quality diagnosis

A retained 31-second, 848×478 room recording exposed a real coverage failure: the initial implementation calibrated each of its 120 frames independently and selected only 48 frames, concentrated in the middle of the clip. Isolated experiments using the same frame features registered 108 frames with shared video intrinsics, then 120 frames in one model with shared intrinsics plus guided matching. The latter had 7,025 sparse points and 1.141-pixel mean reprojection error. These values measure internal image consistency, not independent geometry or face accuracy.

A fresh run through the updated app registered all **120/120 frames** (7,131 sparse points, 1.145-pixel mean reprojection error), completed 7,000 training steps and finished in **462.10 seconds**. Cleanup removed **1,514 of 76,141 splats (1.99%)**, leaving a validated **74,627-splat / 17,613,522-byte** preview. Browser inspection turned through the room and confirmed the seating, doors, TV wall, window, cabinet and table were represented. The view is substantially broader than the previous partial result, but soft boundaries, some stretched artifacts and imperfect people remain visible. This is not proof of complete geometry or accurate faces. Original MP4 playback was also verified in the app. The result was left in preview for user review without replacing an accepted room. No source video, private frame, personal room screenshot or identifying project metadata is included in the public fixture/evidence directories.

Cleanup uses the 90th-percentile sparse-point radius as a scene-relative bound. It removes splats that are exceptionally large, needle-shaped (largest-to-middle scale ratio, preserving thin planes), or far outside that envelope. Above 35% suspected outliers it retains the raw result and warns instead of heavily erasing a scene. Raw exports remain local; verified removal counts and settings survive portable archives. A preliminary shared-camera 7,000-step comparison removed 949 of 64,751 splats. Browser inspection confirmed source-frame alignment and retained room surfaces, while remaining smears were still visible. This heuristic is not a learned deblurring or dynamic-person reconstruction system.

Capture review now labels partial outputs before and during preview, distinguishes unmeasured coverage from a measured zero, and provides original source-video playback after acceptance. Matched-frame percentages are explicitly not physical-room coverage. Moving people, low-resolution faces, blank walls, mirrors and insufficient camera translation remain limitations; the source recording is the faithful reference for people and motion.

## What accuracy means here

**Visual fidelity:** embedded textures and Gaussian rendering are visible in the original fixture screenshots. Those screenshots show the directly generated rendering fixtures, not the new photo reconstruction. Private real-room captures have been visually compared with their reconstructed previews, without surveyed geometry or a calibrated image-quality benchmark. Missing scan areas are not synthesized.

**Scale:** uniform two-point calibration and independent-distance discrepancy calculations are implemented. Known fixture dimensions and transform round trips verify software arithmetic. Declared metre units remain a user assertion; the calibration pair cannot validate itself.

**Anchors:** positions remain in source coordinates across display translation, rotation, uniform scale and saving/reopening. Scan identity is asset UUID plus SHA-256. Changed scans require explicit review. GLB surface anchors refer to imported triangles; splat and manually adjusted anchors remain approximate. No millimetre or centimetre real-world accuracy claim is supported.

**Collision:** the mesh controller tests supporting floors, thin walls, blocked spawn and holes. A separate GLB proxy can be transformed and visually acknowledged for splat navigation. Registration error is not measured numerically. Collision does not certify a complete or accurate physical room.

## Explicit remaining limits

- A physical-room photo collection with independent measurements is needed to establish reconstruction accuracy. Photos, capture guidance and local video frame extraction/reconstruction are implemented; generated completion and guided tours are outside this build. Neither synthetic registration nor the private visual trials establish dimensional accuracy or reliable faces in static 3D.
- Large accepted files may exhaust browser, CPU or GPU memory. Rendering evidence covers small bundled scenes and reconstructions up to about 75,000 splats; no maximum-size stress result is claimed. Walk has a separate 500,000-triangle collision limit.
- PNG fixture display, WAV audio and a 320×180 VP8 WebM video were exercised in Chrome, including explicit playback and absence of autoplay. A retained H.264 MP4 room recording also played successfully in the original-video reference panel. MP3/Ogg signatures are accepted, but their codec playback was not tested. Other media combinations need their own browser check.
- The mobile screenshot is a desktop-browser viewport test; it does not validate touch navigation, mobile GPU capacity or mobile operating systems.
- Upload cancellation aborts the browser request; an operation already committed can still appear in the library. Reconstruction cancellation separately stops the supervised worker process tree and preserves originals. There is one persisted active reconstruction job at a time, with interrupted attempts retained after restart; cancellation does not roll back existing assets or the saved room.
- Recovery restores committed metadata, not missing asset bytes or a corrupted database. Portable archives exclude revision history and include retained originals; full local backups should preserve the whole stopped-server data directory.
- Optional OpenRouter is implemented with explicit content selection, in-memory credentials and review before application. Tests use a mocked transport. Public model pricing and input capabilities were checked against the OpenRouter catalogue. Live authenticated inference, response quality and provider retention behaviour were not verified. Ling 3.1 Flash is the default text-only model; photo assistance requires an explicit free vision-model selection. Zero-price provider caps apply to every request.

## Sparse-frame model assistance

An optional experimental path uses [Depth Anything 3 Base](https://github.com/ByteDance-Seed/Depth-Anything-3) to initialize world-to-camera poses, followed by real SIFT correspondences, triangulation and three rounds of bundle adjustment. The Base model is Apache-2.0 licensed; source revision `3d835ec1a5802d64a8b8b15f817a1ab54809bfe4` and model revision `f4a6c9b3c95e41c82048423d3493a81ec3fa810e` are fixed. Source archive and safetensors are SHA-256 checked. Only bounded camera arrays cross from the separate model process into reconstruction; depth predictions do not become measured surfaces. Training points come from image-feature tracks.

Feasibility experiments on one private capture compared several paths. Direct depth surfaces, confidence-weighted depth fusion and direct Gaussian initialization from learned cameras showed holes, layered surfaces or ghosting and were rejected. With a fixed 24-view subset, conventional mapping registered 13/24 cameras; model initialization followed by feature refinement retained 23/24 supported cameras. This comparison reused previously extracted image features and verified matches, so it is **not** a fresh end-to-end speed benchmark. The 7,000-step 23-view render preserved recognizable room layout and furniture, while soft edges and moving-person smears remained. No surveyed geometry or independent face-fidelity measurements are available.

DA3-only inference at 336-pixel resolution took 7.32 seconds for 24 views and 8.08 seconds for 32 views on the tested M3. Reported Metal driver allocation was about 2.6 GB during those probes. These figures exclude feature processing and Gaussian training and do not establish whole-pipeline peak memory. A separately installed production environment also completed a real 32-view prediction with finite validated camera arrays.

The shipped option limits an attempt to 32 input photos, preserves all originals, rejects points above 4-pixel reprojection error, and excludes cameras below 30 observations. At least three supported cameras and 100 triangulated points are required before training. Unknown archive model paths and download URLs are discarded; model identity and bounded settings survive export/import. Standard stays the default. Unseen-world synthesis remains outside the captured reconstruction; inferred camera estimates and partial input coverage are explicitly labeled.
